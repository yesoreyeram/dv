# Non-functional requirements

IDs use `NFR-<AREA>-<nnn>`. Priority is MoSCoW. "Verification" says how the requirement is
checked; anything listed as CI-enforced must be a failing job when violated.

| NFR-SEC-011 | Containers run as non-root on a distroless/static base, read-only root filesystem, no shell, all capabilities dropped. | M | Dockerfile review; CI image build | In progress |
| NFR-SEC-012 | Panics are recovered per request, logged with a request ID, and answered with a generic `500` (no stack traces to clients). | M | Unit tests | In progress |
| NFR-SEC-013 | Server timeouts: read-header, read, write, idle set; max header bytes bounded (slowloris protection). | M | Unit tests on config | In progress |
| NFR-SEC-014 | Dependencies are minimal and pinned (go.sum, pnpm lockfile); Dependabot enabled. | S | CI `--frozen-lockfile`; review | In progress |
| NFR-SEC-015 | CI supply chain: nothing a workflow fetches can change without a reviewed commit. **AC1:** workflows download files only through `scripts/fetch-verified.sh <https-url> <sha256> <output>`, which fetches over HTTPS into a temporary file, checks it against the SHA-256 given as a 64-hex literal committed in the workflow, and only then moves it to `<output>`; on any failure no output file exists, so an unverified file can never be extracted or run whatever shell control flow surrounds the call. Any other `curl`, `wget`, `aria2c` or `gh release download` in a `run:` script fails the policy (outside shell comments; heredoc text counts, conservatively), as does a helper call whose hash is not a literal. **AC2:** tools run with `go run`/`go install` from outside the module use an exact semver (`@vX.Y.Z`), never `@latest` or a branch, so go.sum/sumdb verify them; every `module/path@version` argument of a `go run`/`go install` command is checked, whatever flags (with or without values) come before it, including the global `-C dir` / `-C=dir` flag placed before the subcommand (`go -C . run …`). Commands are split into words the way the shell does (single and double quotes, backslash escapes; `;`, `&`, `|`, `(`, `)`, backticks and newlines end a command only outside quotes), so a quoted value with spaces or separators (`-C "tools dir"`, `-C "a;b"`) cannot hide the subcommand or the package. Because double quotes do not stop command substitution (`"$(go run …)"`, ``"`go run …`"``), the script is also read a second time with double quotes treated as plain separators, and a finding from either reading counts; only single-quoted text stays literal. Any `go` command with a `run` or `install` word is checked; when unsure, the policy reports rather than skips (so `echo "go run x/y@latest"` is reported too). **AC3:** every `uses:` names a version tag (`@vN`, `@vN.N.N`) or a 40-hex commit SHA, never a branch or no ref; `docker://` images carry an `@sha256:` digest. **AC4:** workflow files pass `actionlint` (with shellcheck) on every PR. **AC5:** AC1–AC3 are enforced by a test over `.github/workflows` that fails CI and by Gherkin scenarios. The test reads `run:` values the way Actions executes them: folded (`>`, `>-`, `>+`) blocks and multi-line plain or quoted scalars are checked with their lines joined by spaces as well as line by line, and a finding from either reading counts.  **AC6:** the vulnerability scan checks the Go standard library that builds the shipped binary: every `govulncheck` invocation in a workflow runs as `GOTOOLCHAIN=local go run golang.org/x/vuln/cmd/govulncheck@vX.Y.Z -show version …` under the `go.mod` toolchain, so a tool that needs a newer Go fails the job instead of the go command silently switching toolchains (a switch sets `GOROOT` for the tool, and the scan then covers the newer toolchain's library, not ours); the step prints the scanned Go version. Enforced by `scripts/check-toolchain.sh` with a drift scenario. | M | `internal/cipolicy` tests; `scripts/check-toolchain.sh` (AC6); `features/repo/ci_supply_chain.feature`; CI `actionlint` job | In progress |
| NFR-SEC-016 | Data-access endpoints that run before authentication exists (M3) are off by default and loopback-only. **AC1:** `queryApiEnabled` defaults to `false`; disabled endpoints answer `404`. **AC2:** enabling them with a non-loopback `httpAddr` (`:8080`, `0.0.0.0`, a LAN IP, a host name other than `localhost`) fails config validation unless `queryApiAllowRemote=true`. **AC3:** with `queryApiAllowRemote=true` a `WARN` is logged at start-up naming the risk. **AC4:** the gate is removed only when NFR-SEC-003 ships. | M | Config unit tests; `query.feature` | In progress |
| NFR-SEC-017 | Pre-authentication data-access endpoints resist DNS rebinding and cross-site requests (B-063). A loopback bind alone does not stop a web page the operator visits from rebinding its own host name to `127.0.0.1` and reading `/api/v1/query` as a same-origin request. **AC1:** while `queryApiAllowRemote=false`, `GET /api/v1/datasources` and `POST /api/v1/query` answer `403 host_not_allowed` unless the request `Host` (port ignored, case-insensitive, trailing dot ignored) is `localhost`, a name ending in `.localhost` (RFC 6761, resolved to loopback by browsers), or a loopback IP literal (`127.0.0.0/8`, `::1`). **AC2:** `POST /api/v1/query` answers `403 cross_site_request` when `Sec-Fetch-Site` is present and not `same-origin` or `none`, or when `Origin` is present and its host:port differs from `Host` (`Origin: null` counts as different). Requests without these headers (curl, server-side clients) are not affected. **AC3:** both checks run before the request body is read and before any query runs; the 403 body never echoes the rejected Host or Origin. **AC4:** with `queryApiAllowRemote=true` AC1 is skipped (the operator chose to expose the API on other host names) but AC2 still applies. | M | `internal/server` unit tests; `features/query/gate.feature` | In progress |

## Performance & scalability (PERF)

| ID | Requirement | Priority | Verification | Status |
| --- | --- | --- | --- | --- |
| NFR-PERF-001 | Health/readiness endpoints p99 < 10 ms on a single core under 500 rps. **AC1:** an open-loop load of 500 rps for ≥ 2 s against `/healthz` and `/readyz` (full middleware chain, real TCP, `GOMAXPROCS=1`) yields only 200s and p99 < 10 ms. **AC2:** under the same load with a readiness check that takes 50 ms, the check runs at most once per readiness-cache TTL (+1), p50 and p99 stay < 10 ms once the first evaluation has completed (one warm-up probe), because later refreshes run in the background (FR-002 AC7). **AC3:** `go test -bench` benchmarks exist for both probes so regressions are visible (`make bench`). | S | `internal/server/perf_load_test.go` (build tag `perf`, own CI step without `-race` so no other package competes for the core) + `features/api/health.feature` (godog step); `make perf`, `make bench` | In progress |
| NFR-PERF-002 | Stateless API nodes; horizontal scaling behind a load balancer (state in DB/cache). | M | Architecture (ADR-0001) | In progress |
| NFR-PERF-003 | Query execution is streaming/bounded: row and byte limits per query, configurable. The byte limit must not under-estimate retained memory by more than 1.6×, and sources apply safe default limits when a query sets none. **AC1 (host limits):** `queryMaxRows`/`queryMaxBytes` in config (must be > 0) are passed to every source as defaults and applied by the query API to every query; a query may only lower them (FR-016 AC6). **AC2 (per-request budget):** the byte limit is a budget shared by all queries of one query-API request, so retained result memory per request is bounded by `queryMaxBytes` (× the ≤1.6× estimate error), not by `queries × queryMaxBytes` (FR-016 AC9). | M | Tests; `query.feature` | In progress (frame builder limits, host limits) |
| NFR-PERF-004 | Initial UI JS bundle ≤ 250 KB gzip; routes code-split as they grow. **AC1:** after `vite build`, the gzip size of every script `index.html` loads up front (entry `<script type="module">` plus `<link rel="modulepreload">`) is summed, and the build fails if it exceeds 250 KB (256 000 bytes); the check also fails if no initial script is found, so a broken build cannot pass vacuously. **AC2:** initial CSS is reported (budget 50 KB gzip) and enforced the same way. | S | `pnpm --filter web run size` in CI after the build | In progress |
| NFR-PERF-005 | Large result frames stay responsive in the browser. **AC1:** the table panel renders only the current page of rows, so the DOM never holds more than 50 data rows whatever the frame size. **AC2:** sorting a 100 000-row numeric column completes in under 500 ms in the unit-test environment (jsdom, single core). | S | Vitest | In progress |
